## The Problem This Solves

When data from three business systems tells three different stories, the organisation stops trusting its own numbers. Finance has one revenue figure. Operations has a different view. Sales has a third. Resolving the differences takes hours every week, decisions are delayed, and nobody is confident in the dashboards.

This project is a full medallion data pipeline that solves that problem:

- **Ingests** raw data from three source systems, each with different conventions
- **Cleans and harmonises** the data: standardises date formats, strips system-specific ID prefixes, deduplicates, handles nulls
- **Builds single agreed metric definitions** that all teams can rely on
- **Runs 26 automated quality checks** across every layer before anything reaches a dashboard
- **Publishes a live dashboard** on GitHub Pages, automatically updated on every push via CI

## Source System Challenges

Each source system was built independently with different conventions. This is what the pipeline resolves:

| Challenge | Finance System | Ops System | Sales System |
|---|---|---|---|
| Date format | `DD/MM/YYYY` | `YYYY-MM-DD` (ISO) | `MM-DD-YYYY` (US) |
| Customer ID | `FIN-C001` | `C001` | `SALES-C001` |
| Duplicates | Yes (billing errors) | No | No |
| Nulls | Missing customer names | Missing delivery dates | Missing industry |
| Revenue | Invoiced amount | N/A | Contract value (differs from invoiced) |

**After the silver layer:** all three systems share a canonical `customer_id` (`C001`, `C002`, etc.) and ISO dates. The gold layer joins them cleanly.

## Gold Layer: Metric Definitions

Every metric in the gold layer has a single agreed definition, documented here and in the SQL files.

| Table | Definition |
|---|---|
| `gold.monthly_revenue` | Invoiced revenue (Paid + Pending only) by month and region |
| `gold.customer_health` | Per-customer view joining finance, ops and sales on canonical `customer_id` |
| `gold.operational_kpis` | Single-row executive summary: total invoiced, paid, payment rate, invoice count |
| `gold.sla_by_region` | On-time delivery rate by region (delivered orders only) |
| `gold.product_revenue` | Revenue and order volume by product |

**Health Score formula:** `(paid_amount / total_invoiced * 50) + (delivered_orders / total_orders * 50)`
A score of 100 = fully paid and 100% on-time delivery.

## Quality Tests (26/26 passing)

Tests are grouped by layer:

**Bronze (6 tests):** Row count thresholds, ingestion metadata columns present

**Silver (9 tests):**
- Deduplication: silver row count less than bronze (duplicates removed)
- No duplicate `invoice_id` after cleaning
- Null date check after `DD/MM/YYYY` parsing
- Customer ID prefix stripping (`FIN-`, `SALES-`)
- `payment_status` only contains valid values
- No negative `total_amount`
- No null `delivery_date` for Delivered orders
- No null `close_date` after `MM-DD-YYYY` parsing

**Gold (11 tests):**
- All 5 tables exist and are non-empty
- `operational_kpis` has exactly 1 row
- `payment_rate_pct` is between 0 and 100
- Revenue reconciliation: gold total matches silver (tolerance less than £1)
- All 8 customers present in `customer_health`
- SLA rates in valid range
- No null health scores

## How to Run Locally

**Requirements:** Python 3.9+

```bash
# 1. Clone the repo
git clone https://github.com/olayinkabello/operational-data-platform.git
cd operational-data-platform

# 2. Install dependencies
pip install -r requirements.txt

# 3. Generate synthetic source data
python scripts/generate_raw_data.py

# 4. Ingest into bronze layer
python scripts/ingest.py

# 5. Run silver and gold transformations
python scripts/transform.py

# 6. Run data quality tests (26 checks)
python tests/test_quality.py

# 7. Export dashboard data
python scripts/export_dashboard_data.py

# 8. Open docs/index.html in your browser to view the dashboard
```

## CI/CD

GitHub Actions runs on every push to `main`:

1. Installs dependencies
2. Generates raw data
3. Runs bronze ingestion
4. Runs silver and gold transformation
5. Runs 26 quality tests (pipeline fails if any test fails)
6. Exports dashboard JSON
7. Deploys to GitHub Pages

The pipeline will fail CI if any quality test fails. This is intentional: broken data should never silently reach a dashboard.

## Why This Matters

The shift from "data as a source of arguments" to "data as a foundation for action" requires three things:

1. A pipeline that handles the messy reality of multi-source data
2. Automated quality gates that catch problems before they reach reports
3. Single agreed definitions that every team uses consistently

This project demonstrates all three. Every component is production-pattern code: typed schemas, idempotent SQL, automated tests, CI, and a live dashboard. No black boxes, no manual steps.
